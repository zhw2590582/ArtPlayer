## 覆盖与测试设计

新增 `test/browser/danmuku-fullscreen.spec.js`：冻结 npm 核心 5.4.0/当前源码核心，
冻结 npm 弹幕 5.3.0/当前源码插件，CSS 网页全屏/真实 document 全屏，三个引擎。
每项连续创建三个独立播放器；每个播放器使用真实视频与原生 Worker，按媒体时间
加载可见弹幕，检查全屏图层宽度、设置/热力图单例、退出后的宽度恢复，以及销毁后
Worker 恰好终止一次、DOM 无残留。候选还检查 scheduler.frame/operation 清空。
文件/包哈希和每轮快照写入附件；不能把三个生命周期称作三小时耐久测试。

45 秒单项上限为新增三轮播放/全屏操作预留，没有增大旧用例的超时，也没有重试、
强制点击、伪造媒体事件、替换全屏 API 或跳过某个浏览器。兼容覆盖 API-04/05/07/08。

`danmuku-stability.spec.js` 的原有三轮 14 秒、每秒 2/20 条负载现在增加核心版本轴，
附件增加 core 字段，原候选逐条采样/显示/回收、状态池、节点复用和 Worker 断言不变。
本轮只运行新增旧核心子集；既有候选核心证据仍标明其实际运行日期与源码哈希。

## 首轮失败与修正依据

1. Chromium 首轮 3 通过、5 失败：旧插件保留同名隐藏测量节点，纯文本定位违反
   唯一性；改为精确文本与可见节点交集，仍要求实际可见。旧核心销毁后留下的全屏
   监听器通过测试的 window 全局数组写入下一实例记录；改为实例局部数组，并保留
   每个旧实例后续收到的事件。BASE-LIFE-18 已在 CORE-16 复现和修复；冻结旧核心的
   三个实例分别观察三轮/两轮/一轮事件，新核心的每个实例只能收到自己的一轮。
2. 三引擎首轮 20 通过、4 失败：WebKit 原生退出时 fullscreenElement 和布局先恢复，
   change 事件稍后投递；测试提前 destroy 抑制了候选的后续通知。现在在销毁之前
   使用原有 7 秒 expect 上限等待真实 [true,false] 事件序列，并继续精确断言次数。
   这不是在缺少事件时跳过检查，也不是对生产代码增加延时。

两份失败报告、trace 和错误断言均保留。后续报告不覆盖它们，见机器证据中的路径及哈希。

源码 72 次、main/legacy 各 36 次播放器生命周期；每个格式重新创建样本，不能
把累计次数当作一个播放器的长期稳定性证明。main/legacy 使用实际工作区分发字节，
不是仓库外安装验证；证据脚本核对加载 SHA 与对应 dist 文件完全一致。

完整快照见 [全屏证据](../baselines/danmuku-fullscreen-validation.json)和
[旧核心负载证据](../baselines/danmuku-old-core-load-validation.json)。本轮候选普通
负载三轮完整显示/回收 72 条，分配 3 节点、复用 69 次；密集负载完整处理 720 条，
分配 21–22 节点、复用 698–699 次。全部 Worker 正常终止，销毁后播放器根节点为零。

对照07的候选核心报告，先核验原报告哈希以及新旧报告加载的插件字节完全一致。
候选插件的 RAF 帧间隔 P95：Chromium 本轮 16.7/16.8ms，原报告 16.7/16.7ms；
Firefox 两档均约16.68ms；WebKit 本轮61/79ms，原报告61/80ms。WebKit在这台
Windows测试环境中本来就没有60fps，旧插件本轮62/79ms；不能把该差异隐去或声称
所有引擎流畅60fps。原始周期级帧间隔也保留，跨周期总体统计明确包含暂停间隙。
这些是不同时间运行的有限样本，没有随机化/同时运行对照，不能宣称因果性能提升。
也未用未强制GC的heap读数证明不存在泄漏。
